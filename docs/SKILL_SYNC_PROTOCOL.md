# Auday Skill Sync Protocol (Connect to your workflow)

How the official Auday Skill (desktop, 0.3.x) reads an iPhone's Auday data over the local network, once the phone's "Connect to your workflow" page allows it. The replica's Mac web app plays the phone's part ([`app/workflow_server.py`](../app/workflow_server.py), [`app/workflow_link/`](../app/workflow_link)). Derived from the Skill's behaviour; contains none of its code.

- **TLS-PSK**: encryption keyed from a shared secret (the communication password) instead of certificates.
- **Snapshot**: a frozen copy of the phone's data, downloaded page by page.
- **Lease**: a short-lived claim on a snapshot, so the phone doesn't replace it mid-download.

## 1. Roles

| | Phone (server) | Skill on the computer (client) |
|---|---|---|
| Discovery | Advertises `_auday-link._tcp` over Bonjour, domain `local.` | Browses for 3 seconds and lists service names (unauthenticated) |
| Authentication | TLS-PSK key made from the communication password | Same password, stored in Keychain / Windows Credential Manager |
| Data | Read-only snapshots, two scopes | Pulls page by page, validates, then commits everything at once to local SQLite |

Each request uses its own TCP connection: connect, TLS handshake, send one request frame, read one reply frame, disconnect.

## 2. Discovery

- Service type `_auday-link._tcp`, domain `local.`. The service name is for humans (usually the device name on the phone), at most 63 bytes.
- `discover` returns `{"services": [...], "authenticated": false}`. Names are not authenticated; the handshake is.
- `pair` and later requests connect by service name (Bonjour resolution) or directly with `--host/--port`.
- macOS also has experimental Apple peer-to-peer Wi-Fi. Both sides must turn on `includePeerToPeer`; it is off by default.

## 3. Communication password and TLS-PSK

- **Password:** 16 random characters generated by the phone, 80 bits. Alphabet `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (32 characters; no 0, 1, I, O). Shown as `XXXX-XXXX-XXXX-XXXX`.
- **Normalization:** uppercase, then strip whitespace and `-`. The result must be exactly 16 alphabet characters with at least 4 distinct ones. Otherwise the client rejects it (`use_generated_16_character_communication_password`).
- **Key:** `HKDF-SHA256(ikm = normalized password, salt = "auday-workflow-link-v2", info = "tls-psk", length 32)`.
- **PSK identity:** `auday-workflow-link-v2`.
- **TLS:** 1.2 only (min and max), single cipher suite `TLS_ECDHE_PSK_WITH_CHACHA20_POLY1305_SHA256` (0xCCAC). No certificates, no plaintext fallback, no 0-RTT. The client adds `transport: {"tlsVersion": "0x0303", "cipherSuite": "0xccac"}` to its results.
- **Wrong password:** the handshake fails and the client only sees a timeout or connection failure (`awaiting_phone_or_wrong_password` / `authentication_or_connection_failed`).
- **Shared credential:** all authorized computers use the same password. There are no per-computer credentials and no revocation. Changing the password or turning off access only blocks future reads.

### Pairing

`pair` runs only in a local terminal:

1. Reads the password from `/dev/tty` without echo (on Windows, from a newly opened console).
2. Sends one `{"op":"status"}` with it. Pairing succeeds only if the reply is `ok: true`.
3. Stores the password in Keychain: service `ai.auday.workflow-link.experimental`, account derived from a hash of the profile directory path.
4. Writes the connection method (service name or host/port) to the profile's `connection.json`.

The password never appears in command arguments, chat or files.

## 4. Frames

- A frame is a 4-byte big-endian length followed by a UTF-8 JSON object. Length: 1 byte to 2 MiB (2 097 152).
- Requests and replies are JSON objects, never arrays.
- Every reply has `ok`. Failure is `{"ok": false, "error": "<code>"}`; the client passes `error` through unchanged.
- Every successful reply includes `sourceDeviceID`. The client stores it on first sync. Any later reply with a different value fails with `source_device_changed` (each phone needs its own profile).

## 5. Status and capabilities

`{"op": "status"}`, optionally with `lease`. Fields the client reads:

| Field | Meaning |
|---|---|
| `schemaVersion` | Must be `1` |
| `sourceDeviceID` | Non-empty string (an uppercase UUID on the real phone) |
| `access` | `text-only-read-only` (all text) or `text-and-audio-read-only` (text and audio) |
| `capabilities` | Object, see below |
| `snapshotState` | `idle` (never prepared) / `preparing` / `ready` / `failed` |
| `snapshot` | Snapshot identifier, 64 lowercase hex characters; null when `idle` |
| `recordCount`, `assetCount` | Integers, 0 to 1 000 000; `assetCount` must be 0 in the text scope |
| `snapshotCapturedAt` | When the snapshot was taken; stored by the client as `sourceSnapshotAt` |
| `snapshotCurrent` | Boolean: is this snapshot still the phone's latest content |

Capability flags (all `true` on the real phone):

| Capability | Client behavior |
|---|---|
| `onDemandSnapshot` | Sends `prepareSnapshot` before syncing and waits for `ready` |
| `snapshotLeases` | Holds a lease while preparing and reading, so the snapshot isn't swapped mid-transfer |
| `retainedSnapshots` | Phone keeps several snapshots, so another computer's sync doesn't interrupt this one |
| `chunkedRecords` | List requests send `allowRecordChunks: true`; large records download in chunks |
| `onDemandAudio` | Audio catalog is lightweight; each asset needs `prepareAudio` before download |

## 6. Syncing a snapshot

```
status
prepareSnapshot {retry: true, useSnapshotLease: true}   → status fields + lease
  (while snapshotState is preparing, send status {lease} every 0.25 s, up to 120 s)
list   {offset, snapshot, lease, allowRecordChunks}      → {snapshot, records[≤100], nextOffset}
  ...until nextOffset is null
  for rows with recordTransfer: fetch the full record chunk by chunk with recordChunk
assets {offset, snapshot, lease}                         → {snapshot, assets[≤100], nextOffset}
status                                                   → only checks snapshotCurrent, does not prepare again
releaseSnapshot {lease}
```

- **Prepare:** `prepareSnapshot` is sent once per sync, even if new recordings arrive. Progress and outcome come through `status`: failure is `snapshot_preparation_failed`, timeout is `snapshot_preparation_timed_out`.
- **Lease:** a UUID string (the client checks the format). Every later `list` / `assets` / `read` / `recordChunk` / `prepareAudio` / `audio` request carries `snapshot` and `lease`. `releaseSnapshot` is sent on success and on failure; unreleased leases expire and the phone reclaims them.
- **Paging:** at most 100 rows per page; fewer is fine (the replica cuts pages by frame size). `nextOffset` must equal `offset` + rows on this page, and is null on the last page. The reply's `snapshot` must match the request, otherwise `snapshot_changed`.
- **Validation:**
  - Record and asset counts equal the counts in `status`.
  - Every row has a non-empty, unique `id`.
  - Record `kind` is one of `transcript`, `highlight`, `summary`, `reflection`, `memory`.
  - In the text scope, records carry no `audioAssetID` / `audioAssetIDs`.
- **Commit:** after validation, the local records and assets tables are replaced in one transaction. If snapshot identifier, counts and scope are all unchanged, no record bodies are transferred.
- **Scope:** the snapshot identifier includes the access scope, so switching scope produces a new snapshot.

### Large records (chunkedRecords)

A large record appears in the list as a placeholder row:

```json
{"id": "...", "kind": "transcript", "recordTransfer": {"encoding": "json-utf8", "size": 1234567, "sha256": "<64 hex>"}}
```

- `size` is 1 byte to 128 MiB.
- Request: `recordChunk {id, snapshot, offset, length ≤ 262144}`. Reply: `{snapshot, id, offset, size, sha256, data(base64), chunkSHA256}`.
- The client checks each `chunkSHA256`, then the overall `sha256`, then parses the JSON into the full record. Its `id` must match, and it must not contain another `recordTransfer`.
- An interrupted download resumes from the bytes already received.

## 7. Record shape

Every record has `id`, `kind`, `payload`, `start`, `state`, `text`, `timeZone`, `timeZoneBasis` and `title`. The client sorts by `start`, searches keywords in `text + title`, and matches `--date` against the ISO date stored verbatim in `start`.

| kind | state | Notes |
|---|---|---|
| `transcript` | `saved` | One per snippet; has `end`; has `audioAssetIDs` in the text-and-audio scope |
| `summary` | `saved` / `saved-overview` | Two per hour: the Summary body, and a short title + information density |
| `highlight` | `complete` | Has `end`, `hourStart`, `generatedAt` |
| `reflection` | `complete` | One per day, split at local midnight; `savedVersion` |
| `memory` | `confirmed` / `automaticallySaved` / `candidate` / `rejected` / `superseded` / `inactive` | `payload` holds the source, promotion date and `supersedes` |

Field details: [`app/auday_export.py`](../app/auday_export.py) and [AUDAY_OBSERVATIONS.md](AUDAY_OBSERVATIONS.md).

## 8. Audio

### Catalog

Only `text-and-audio-read-only` has an audio catalog. A row on the real phone (on-demand preparation):

| Field | Example / format |
|---|---|
| `id` | `audio-` + 64 hex characters |
| `contentRevision` | 64 hex characters; changes when the content changes |
| `duration` | Seconds (float); one segment is at most about 900 s (15 minutes) on the real phone |
| `fragmentID`, `regionID`, `sessionID` | Uppercase UUIDs |
| `start` | ISO time with milliseconds and time zone offset |
| `timeZone` | IANA time zone |
| `preparation` | `on-demand` |

Assets that aren't on-demand carry `size` and `sha256` directly. A catalog row doesn't mean the audio has been downloaded.

### On-demand audio

```
prepareAudio {id, snapshot, lease}              → {snapshot, asset: catalog row + mime, size, sha256, timeline}
audio {id, offset, length ≤ 262144, snapshot, lease}
                                                → {snapshot, offset, size, sha256, data(base64), chunkSHA256}
```

- `mime` is one of `audio/mp4`, `audio/wav`, `audio/x-wav`, `audio/x-caf`, `audio/aac`. The real phone serves AAC in a CAF container (mono, 48 kHz, about 32 kbps) as `audio/x-caf`.
- `timeline` is a non-empty array of `{fileStart, fileEnd, recordedStart}`: a range of seconds in the file (`0 ≤ fileStart < fileEnd`) mapped to the recording start time with time zone.
- `audio` before `prepareAudio` returns `audio_not_prepared`; the client then prepares once more.
- Each chunk is checked against `chunkSHA256` and the finished file against `sha256`. A `.asset.json` next to the file keeps the source and timeline. Interrupted downloads resume.
- In the text scope every audio request returns `audio_access_denied`.

## 9. Error codes

Codes the client shows hints for: `snapshot_not_ready`, `snapshot_changed`, `snapshot_busy`, `snapshot_preparation_failed`, `snapshot_preparation_timed_out`, `audio_access_denied`, `audio_not_prepared`, `record_chunk_hash_mismatch`, `record_hash_mismatch`, `audio_hash_mismatch`, `source_device_changed`, `invalid_snapshot_lease`, `invalid_page`, `invalid_cursor`, `incomplete_snapshot`.

## 10. Replica implementation

- **Settings → Workflow → Connect to your workflow.** Turning on "Allow the Skill to read" starts advertising. Scope is "All text" or "Text and audio", both read-only. A password is generated the first time; you can generate a new one or enter your own 16 characters (they must follow the alphabet rules above or the Skill rejects them). The password shows only on this machine's settings page (`/api/workflow` accepts local requests only) and is masked in `/api/settings`.
- **TLS-PSK and Bonjour.** Python 3.12 has no TLS-PSK server. A small Swift program (`app/workflow_link`, using the Network framework like the phone) advertises the service, does the handshake, and forwards the decrypted stream to a private Python Unix socket (directory permissions 0700). It gets the password on stdin, not in arguments, and is compiled with the Xcode Command Line Tools the first time access is turned on.
- **Snapshots.** Built from `auday_export.library(app)`, records sorted by `(start, id)`. The identifier is the SHA-256 of the content (including device ID and scope), so unchanged content keeps its identifier and the Skill doesn't download again. The 4 most recent snapshots are kept. Leased snapshots are never evicted; if all 4 are leased, a new preparation returns `snapshot_busy`. A lease expires after 10 minutes unused.
- **Large records.** Records over 256 KiB serialized use `recordTransfer`. Pages are also cut at about 1.5 MiB to fit in one frame.
- **Audio.** The catalog lists recordings the replica has saved and still keeps (within the retention period). `prepareAudio` converts WAV to CAF/AAC with macOS's built-in `afconvert` (like the phone) and caches it in `data/cache/workflow-audio/`. Without `afconvert` it serves WAV. The timeline is one segment: `{0, duration, recording start time}`.
- **Read-only.** No operation writes, deletes, controls recording or triggers generation.

## 11. Tests

- `tests/test_workflow_server.py`: password rules, frame encoding and decoding, paging coverage, frame size, chunked large records, stable snapshot identifiers, lease protection, both scopes, and chunk checks for on-demand audio. Synthetic data only.
- `scripts/workflow_skill_e2e.py`: runs the real flow with the installed official Skill CLI (discover → pair → status --live → sync → search → assets → audio) in both scopes. It uses a throwaway Skill profile and password, then deletes the profile directory and its Keychain entry. The real phone's pairing is untouched.
